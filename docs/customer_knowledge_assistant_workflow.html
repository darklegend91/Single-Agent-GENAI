System workflow · local reference implementation

Customer Knowledge Assistant

This app loads customer records into a local source store, then answers questions for an authorized customer. Exact field and revenue questions use deterministic SQLite tools; broader questions use customer-filtered retrieval and a bounded Ollama agent. Every answer carries its customer ID, status, evidence, and limitations.

Streamlit UI→FastAPI + access checks→SQLite + Milvus Lite→Ollama / Pydantic AI→Evidence-checked answer
00 / HIGH LEVEL

One local app, two data paths

This is the current single-host workflow started by scripts.run_local. The CSV is validated once into the complete SQLite source; compact summaries are embedded into Milvus Lite. Each question passes through FastAPI authorization, then uses either exact authorized data access or customer-filtered semantic retrieval. Cross-cutting bars show the security and telemetry controls.

The high-level view describes the local profile that python -m scripts.run_local starts. It does not claim a production cloud topology. The API, UI, Ollama, SQLite, and Milvus Lite may each have different readiness requirements.
01 / INGEST

Build one active customer snapshot

The local runner first ingests the configured CSV. SQLite keeps every validated source row for exact, customer-ID lookups. A compact set of summaries is embedded into Milvus Lite for discovery. The active manifest ties the source database and vector index to one versioned snapshot.

Why two stores?

SQLite is complete; Milvus is a compact discovery index.

Exact customer lookup and financial arithmetic use the authorized SQLite source row. Milvus supplies semantic discovery over embedded summaries. With the local runner’s default 100-summary index, a customer outside Milvus is still fetched by exact ID from SQLite; the index limit controls semantic coverage, not customer availability.

Consistency rule

One active manifest

The manifest binds the SQLite file, vector collection, schema, embedding configuration, checksum, and dataset version. Failed staging leaves the prior active snapshot in place.

02 / QUESTION

Answer one authorized customer question

The ID in the question can override the sidebar selection. FastAPI checks the identity and customer scope before any data access. The router then chooses a direct, deterministic tool path or a broader retrieval-plus-agent path; both converge on evidence validation before the UI displays an answer.

Exact fast path

Use deterministic tools when possible.

Known field questions and monthly revenue can read authorized SQLite values directly. Financial amounts remain integer paise, and the response renderer formats them without binary floating-point arithmetic.

Broader RAG path

Retrieve narrowly, answer with evidence.

Milvus applies the requested customer filter before top-K. Context is limited to relevant fields and a token/character budget. The single Pydantic AI agent gets fixed read-only tools; Ollama runs locally.

Answer contract

Every response names its customer.

The validator checks user ID, metric or source field, value, and unit against authorized tool results. Unsupported claims become insufficient-evidence responses or explicit limitations.

03 / TRUST + VISIBILITY

Controls run across the workflow

These protections are enforced at the point where they matter; the model is never the authority for access, source values, or whether a claim is supported.

01 · Identity

Scope before data access

FastAPI authenticates a configured bearer identity and checks the customer ID. Tools and retrieval independently authorize that ID; a model request cannot expand the scope.

02 · Retrieval

Filter, then verify

Milvus search is customer-filtered. Returned metadata is checked against the active dataset version, schema, source checksum, and embedding configuration before context is built.

03 · Output

Evidence or a clear limitation

Input and output guardrails block unsafe requests and unsupported facts. The UI shows status, customer ID, source evidence, and limitations so users can judge what the data supports.

04 · Observability

Langfuse sees operational metadata, not customer content.

Allowlisted trace metadata can include stage timings, outcome, evidence presence, tool/request counts, and provider token counts when available. Questions, prompts, answers, records, and credentials are excluded. Accuracy scores are grounding/validation signals; a defensible factual-accuracy percentage requires a reviewed labeled test set.

Current dashboard note

The linked project’s recent window showed request, authentication, and final-status spans, but no retrieval or model-generation observations. Its current dashboard is useful for request health; RAG/model performance needs those spans to appear first.

Run locally

One command starts the stack.

python -m scripts.run_local loads/reuses the dataset, then starts FastAPI on port 8000 and Streamlit on port 8501. Ollama must be available with the configured chat and embedding models.

Other Streamlit tabs

Customer details, Revenue, and Security & accuracy

Customer details and Revenue load authorized customer summaries and deterministic monthly metrics. Security & accuracy shows backend readiness, grounding/performance signals, and Langfuse connection status. These views use the same backend identity and active snapshot as chat.

05 / RADAR · SPIDER

Compare the app’s three answer paths

The axes compare the implementation shape of the exact chat fast path, the broader RAG/agent path, and the direct customer/revenue views. A higher mark means more of that capability by design.

Rating key · ordinal 1–5

Qualitative architecture profile, not a performance result.

Ratings reflect the code path: exact and dashboard views avoid model generation, so they rank high on expected speed, determinism, and model independence. The broader RAG path covers semantic questions, but adds vector retrieval and local generation. All paths can return evidence; exact-value claims remain grounded in authorized source data.
